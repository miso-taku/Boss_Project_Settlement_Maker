# F3: 入力フォーム（依頼文・残り時間・優先度・制約）— 設計

## 方針

- **DDD 境界**: フロントエンドのフォームは UI 都合（表示制御・入力補助・UX）に集中する。業務ルール（バリデーションの最終判断）はバックエンド（Domain）に寄せる。
- **責務分割**: フォームコンポーネントは「入力フィールドの表示・状態管理・基本的なバリデーション」に集中する。API 呼び出し・エラー表示・ローディング表示は F4/F5 で実装する。

## データフロー

```
[ユーザー]
  → フォームに入力（依頼文・残り時間・優先度・制約）
  → React state で状態管理
  → [F4 で実装] 生成実行ボタンをクリック
  → API クライアント関数を呼び出し
  → バックエンド（FastAPI）で処理
```

## API変更

- 今回は API 変更なし。既存の `POST /api/v1/reply-drafts` エンドポイントを利用する。
- **リクエスト**: `GenerateReplyDraftsRequest`
  - `request_text`: string（必須・非空）
  - `remaining_hours`: number | null（任意・0以上）
  - `priority`: "high" | "medium" | "low" | null（任意）
  - `constraints`: string（任意・空文字可）

## 代替案と採用理由

- **フォーム管理: React Hook Form vs 標準 React state**: 今回は標準の React state（`useState`）を使用する。F3 ではフォームの入力のみを実装し、API 呼び出しは F4 で実装するため、状態管理が比較的シンプル。React Hook Form は必要に応じて F4 以降で導入を検討する。**標準 React state を採用**。
- **コンポーネント配置: page.tsx 直接 vs 別コンポーネント**: フォームコンポーネントを `frontend/src/components/` 配下に別ファイルとして作成する。再利用性・テスト容易性を考慮。**別コンポーネントを採用**。
- **優先度入力: ラジオ vs セレクト**: 3段階の選択肢なので、ラジオボタンを使用する。視認性が高く、選択肢が少ないため適切。**ラジオボタンを採用**。
- **残り時間入力: 数値入力 vs スライダー**: 数値入力フィールド（`type="number"`）を使用する。単位（時間）を明示する。**数値入力フィールドを採用**。

## テスト戦略

## 結果と学び（モード3）

- **採用案の妥当性**: 標準の React state（`useState`）を使用した実装は、F3 ではフォームの入力のみを実装するため、状態管理が比較的シンプルで適切だった。フォームコンポーネントを別ファイルとして作成することで、再利用性・テスト容易性を確保できた。ラジオボタンを使用した優先度選択は、3段階の選択肢に適しており、視認性が高かった。
- **想定外**: `npm run lint` の実行環境に問題があり、lint の実行ができなかったが、TypeScript の型チェックで問題がないことを確認できた。テスト実行は F6 でテスト設定を追加予定のため、今回はテストファイル作成のみで完了とした。
- **改善点**: 次回（F4）で生成実行ボタンと API 呼び出しを実装する際に、フォームの状態を親コンポーネント（`page.tsx`）に持ち上げるか、フォームコンポーネント内で API 呼び出しを行うかを検討する必要がある。また、F5 でエラーハンドリングを実装する際に、バリデーションエラーの表示方法を統一する必要がある。スタイリングについては、現在はインラインスタイルで実装しているが、必要に応じて CSS Modules や Tailwind CSS の導入を検討する。
