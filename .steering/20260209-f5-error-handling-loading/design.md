# F5: エラーハンドリング・ローディング表示 — 設計

## 方針

- **DDD 境界**: フロントエンドは UI 都合（表示制御・入力補助・UX）に集中する。エラーハンドリングは UI 層で実装し、ユーザーフレンドリーなメッセージに変換する。
- **責務分割**: `ReplyForm` コンポーネントでエラー状態・ローディング状態を管理し、エラー表示・ローディング表示を実装する。API クライアント（`replyDrafts.ts`）で HTTP エラー・ネットワークエラーの詳細情報を取得し、適切なエラーオブジェクトを返す。
- **状態管理**: React state（`useState`）でエラー状態・ローディング状態を管理する。エラー情報は、エラータイプ（HTTPエラー、ネットワークエラー、バリデーションエラー等）とメッセージを含むオブジェクトとして管理する。

## データフロー

```
[ユーザー]
  → 生成実行ボタンをクリック
[ReplyForm コンポーネント]
  → ローディング状態を true に設定
  → スピナー/プログレスバーを表示
  → API クライアント関数（generateReplyDrafts）を呼び出し
[API クライアント（replyDrafts.ts）]
  → fetch API でリクエスト送信
  → HTTP エラー（4xx, 5xx）の場合: エラーレスポンスを解析し、適切なエラーオブジェクトを返す
  → ネットワークエラーの場合: ネットワークエラーオブジェクトを返す
  → タイムアウトの場合: タイムアウトエラーオブジェクトを返す
[ReplyForm コンポーネント]
  → エラーオブジェクトを受け取る
  → エラータイプに応じて適切なエラーメッセージを表示
  → ローディング状態を false に設定
  → スピナー/プログレスバーを非表示
```

## API変更

- 今回は API 変更なし。既存の `POST /api/v1/reply-drafts` エンドポイントを利用する。
- **エラーレスポンス**: FastAPI の標準的なエラーレスポンス形式を想定
  - `400 Bad Request`: `{"detail": "バリデーションエラーメッセージ"}` または `{"detail": [{"loc": [...], "msg": "...", "type": "..."}]}`
  - `404 Not Found`: `{"detail": "リソースが見つかりません"}`
  - `500 Internal Server Error`: `{"detail": "サーバーエラーが発生しました"}`
- API クライアントでエラーレスポンスの `detail` フィールドを取得し、適切なエラーメッセージに変換する。

## 代替案と採用理由

- **ローディング表示: スピナー vs プログレスバー vs スケルトンローディング**: スピナーを採用する。実装が簡単で、視覚的なフィードバックを提供できる。プログレスバーは進捗が不明な場合（API 呼び出し）には適さない。スケルトンローディングは返信案表示エリアの形状が固定されていないため、今回は採用しない。**スピナーを採用**。
- **スピナー実装: CSS アニメーション vs ライブラリ**: CSS アニメーションで実装する。追加のライブラリが不要で、軽量。**CSS アニメーションを採用**。
- **エラーメッセージ表示: インライン表示 vs トースト vs モーダル**: 既存のインライン表示（F4 で実装済み）を改善する形で実装する。トーストライブラリの導入は検討するが、今回は基本的な実装のみとする。モーダルはエラーの重要度が高くないため、採用しない。**インライン表示を採用**。
- **エラー情報の管理: 文字列 vs オブジェクト**: エラータイプ（HTTPエラー、ネットワークエラー、バリデーションエラー等）とメッセージを含むオブジェクトとして管理する。これにより、エラータイプに応じた適切な表示が可能になる。**オブジェクトを採用**。
- **API クライアントのエラーハンドリング: 統一エラー型 vs 個別エラー型**: 統一エラー型（`ApiError` 等）を定義し、エラータイプとメッセージを含む。これにより、エラーハンドリングが一貫性を持つ。**統一エラー型を採用**。

## 結果と学び（モード3）

- **採用案の妥当性**: スピナーを CSS アニメーションで実装したのは、追加のライブラリが不要で軽量であり、適切だった。エラーメッセージの表示は既存のインライン表示を改善する形で実装し、エラータイプに応じた適切なメッセージを表示できるようになった。エラー情報を `ApiError` オブジェクトとして管理することで、エラータイプに応じた適切な表示が可能になり、拡張性も確保できた。`ApiErrorException` クラスを追加することで、後方互換性を保ちながら、エラー情報を構造化して扱えるようになった。

- **想定外**: TypeScript の `tsconfig.json` で `moduleResolution: "bundler"` を使用しているが、これは Next.js 15 の標準設定であり、直接 `tsc` を実行する場合はエラーになる。ただし、`next build` では問題なく動作するため、実際のビルドには影響しない。バリデーションエラーの配列形式（FastAPI の標準形式）に対応する必要があったが、`detail` フィールドが配列の場合の処理を追加することで対応できた。

- **改善点**: エラーメッセージの多言語対応は今回は考慮していないが、将来的に必要になった場合は、エラーメッセージの生成ロジックを国際化ライブラリと統合する必要がある。ローディング表示については、現在はスピナーのみだが、将来的にはプログレスバーやスケルトンローディングの導入も検討できる。エラーハンドリングについては、リトライ機能やオフライン状態の検出など、より高度な機能の追加も検討できる。アクセシビリティについては、`role="alert"` や `aria-live` 属性を追加したが、より詳細な対応が必要になる可能性がある。
