# requirements.md — バックエンド Tidy-First リファクタリング

## 背景 / 目的

- 書籍「Tidy-First?」の考え方に沿い、**外部仕様を変えずに**バックエンドの読みやすさ・変更容易性を高める整頓を行う。
- リファクタリングスキル `.cursor/refactoring-tidy-first/SKILL.md` に従い、小さく安全に整頓を積み上げる。

## スコープ

### やること

- 対象: **backend/** 配下の Python ソース（`src/settlement_maker/` および `tests/` のうちリファクタに伴い調整する部分）。
- 整頓テクニックの適用順:  
  1) 読む順番・凝集の順番  
  2) デッドコード削除・シンメトリー統一  
  3) 説明変数・説明定数・明示的パラメータ  
  4) ステートメント分割・ヘルパー抽出・ひとかたまり調整  
  5) 説明コメント（Why）・冗長コメント削除  
  6) 必要に応じて新IF/旧実装（ラッパ）
- 変更は**挙動不変**（同じ入力→同じ出力）。API 契約・レスポンス形式は変更しない。

### やらないこと

- 大規模なアーキテクチャ変更（ディレクトリ再編・レイヤリング変更）。
- 新機能追加・仕様変更。
- テストが無い状態での大胆な挙動変更。
- フロントエンドの変更（本作業では対象外）。

## 受け入れ条件（Given-When-Then 風）

- **Given** 既存の pytest が通る状態  
- **When** リファクタリング実施後も `uv run pytest -q` を実行する  
- **Then** 全テストがパスし、API の入出力仕様（POST /api/v1/reply-drafts のリクエスト/レスポンス）が変更されていないこと。

## 影響範囲

| 対象 | 内容 |
|------|------|
| BE ソース | `src/settlement_maker/` の各層（domain / application / infrastructure / interface） |
| BE テスト | 必要に応じてリファクタに合わせた最小の調整のみ |
| API/契約 | 変更なし（挙動不変） |
| DB | なし |
| Docs | `./docs/implementation-tasklist.md` に本作業の完了を反映。必要なら `./docs/architecture.md` 等の文言は触らない（仕様変更でないため）。 |

## 未決事項 / リスク / 仮定

- **仮定**: 既存の 31 テストがすべてパスしている状態を「正」とする。リファクタ後も 31 テストがパスすることを確認する。
- **リスク**: 差分が大きくなりすぎないよう、ファイルごと・テクニックごとに小さく進める。
- **未決**: 特になし（挙動不変の整頓に限定）。
